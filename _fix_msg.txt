🐛 修复：产物行尾跨平台不一致（CI 首跑抓出）· 规则内容零改动

根因
convert_ruleset.py 用 write_text(text) 写出，而 Python 的通用换行转换会把
\n 按平台写成 os.linesep —— Windows 出 CRLF、Linux 出 LF，**同一脚本跨
平台产出不同字节**。后果是仓库内行尾分裂（mihomo / Surge 四份产物为 CRLF、
sing-box 两份为 LF），且 CI 在 Linux 上重跑生成必得 LF、与仓库内容不符，
第 6 段「产物可复现」当场判负。

修复（两条腿，缺一不可）
- skill/scripts/convert_ruleset.py：写出改为 write_text(..., newline='')
  显式钉死 LF（该文件只有这一处写出点，单点收口）。
- .gitattributes：新增，声明 * text=auto eol=lf，管住检出与提交。
  只改脚本则仓库内容仍是 CRLF、CI 仍判负；只归一化文件则下次在 Windows
  重跑又写回 CRLF。

产物重跑
六份产物按新脚本重跑。验证方式为「与改动前逐字节归一化行尾后比对」，
结果全部为「仅行尾不同、内容一致」。mihomo-ads.yaml / surge-ads.list
在 diff 中显示整文件改动，是 CRLF→LF 的预期表现。
sing-box 两份 JSON 本就是 LF，无变化。

本次缺陷是 CI 第一次运行当场抓出的
本地全绿、CI 判负 6 项，根因正是平台差异（本机 Windows 的 write_text
出 CRLF，与仓库内容"碰巧"一致；Linux 出 LF 才暴露真相）。这印证了该断言的
价值：「产物 == 源头重跑结果」必须跨平台验证，只在本机跑等于没跑。

同时更正一条此前的错误判断
上一提交的说明里曾写「仓库内实际存的是 LF，只是 core.autocrlf=true 把它
检出成 CRLF」。用 git cat-file -p HEAD:<file> 直读 blob 核实后确认：
仓库内就是 CRLF，core.autocrlf 不是原因。教训是判断「仓库里到底存了什么」
必须直读 git 对象，不能看工作区（工作区会被 autocrlf 改写）。
